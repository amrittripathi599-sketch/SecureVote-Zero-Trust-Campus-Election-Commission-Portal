# SecureVote — STRIDE Threat Model & Security Controls

The STRIDE model (developed by Microsoft) classifies security threats into six distinct categories.
This document outlines the threat landscape for campus elections, specific attack scenarios, and the concrete zero-trust cryptographic and architectural mitigations implemented in SecureVote.

---

| STRIDE Category | Threat Description | Attack Example / Scenario | Implemented Mitigation in SecureVote |
| :--- | :--- | :--- | :--- |
| **Spoofing**<br>*(Identity Theft / Impersonation)* | An unauthorized party attempts to authenticate or cast ballots as another student or election officer. | An attacker discovers a student's institutional roll number and attempts credential guessing or uses a forged identity header. | 1. **Bcrypt Password Hashing**: Passwords stored using bcrypt (12 rounds) with unique salts; plain-text passwords never stored or logged.<br>2. **Cryptographic JWT Tokens**: Signed using HMAC-SHA256 with strong secret validation; claims include subject, role, issuer, and expiration (60 minutes).<br>3. **Brute-Force Rate Limiting**: After 5 failed attempts within 10 minutes, account access is throttled with HTTP 429.<br>4. **Production Key Guard**: System refuses to start in production if `JWT_SECRET` is left as default or shorter than 32 characters. |
| **Tampering**<br>*(Unauthorized State Mutation)* | An attacker modifies votes, alters election parameters, or tampers with candidate policy documents. | An adversary executes `UPDATE votes_ledger SET candidate_id = 1` or uploads a malicious executable disguised as a PDF manifesto. | 1. **Kernel-Level Trigger Immutability**: SQLite & PostgreSQL triggers abort any `UPDATE` or `DELETE` on `votes_ledger` and `audit_logs`.<br>2. **PDF Magic Byte Inspection**: Uploaded manifestos are checked for `%PDF-` binary magic bytes and strictly capped at 5 MB.<br>3. **ACID Transaction Rollback**: If any failure occurs during voting, the entire transaction rolls back completely to prevent phantom states.<br>4. **Parameterized SQL Queries**: All database queries execute via SQLAlchemy 2.0 ORM with parameter binding, preventing SQL injection. |
| **Repudiation**<br>*(Denial of Actions)* | A voter denies having voted, or an administrator denies tampering with election timelines. | A student claims their vote was dropped and attempts to vote a second time, or an admin silently alters election dates without a trace. | 1. **Append-Only Audit Trail**: Every sensitive event (`auth.login`, `vote.cast`, `admin.election.update`, etc.) is recorded with timestamp, client IP, actor identity, action, and outcome.<br>2. **Scope-Specific Participation Table**: `election_participation` records the exact timestamp of participation, proving that the user cast a ballot.<br>3. **Immutable Audit Triggers**: Audit log table cannot be edited or truncated by any application user. |
| **Information Disclosure**<br>*(Privacy & Ballot Leaks)* | Unauthorized parties learn which candidate a specific student voted for, or credentials leak in responses. | A database administrator inspects relational tables to deanonymize who voted for an opposition candidate, or password hashes are leaked via API. | 1. **3NF Ballot Secrecy**: `votes_ledger` contains **NO `user_id` column**, physically severing identity from ballot choice.<br>2. **Stripped API Payloads**: Pydantic response schemas explicitly exclude `password_hash`.<br>3. **Secrecy-Preserving Confirmations**: The vote confirmation endpoint returns only success metadata with zero candidate details.<br>4. **Security Headers Middleware**: Enforces `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Strict-Transport-Security`. |
| **Denial of Service**<br>*(Availability Disruption)* | Attackers overwhelm the portal or flood vote transactions to prevent legitimate students from casting ballots. | A malicious bot script sends concurrent vote requests to trigger race conditions or lock database rows indefinitely. | 1. **Sliding-Window Rate Limiting**: Throttles brute-force login attempts per roll number.<br>2. **Row-Level Concurrency Locking**: Uses `SELECT ... FOR UPDATE` (PostgreSQL) or immediate transactions (SQLite) to serialize submissions and eliminate TOCTOU race conditions.<br>3. **Payload Size Enforcement**: Fast rejection of uploads exceeding 5 MB before buffering memory. |
| **Elevation of Privilege**<br>*(Unauthorized Authorization)* | A standard student voter gains access to administrative election creation or audit controls. | A voter crafts requests to `/api/admin/elections` or attempts to view full audit logs and user rosters. | 1. **RBAC `require_admin` Dependency**: Validates the authenticated user's role on every administrative endpoint, returning strict HTTP 403 Forbidden to non-admins.<br>2. **Frontend Role-Based Routing**: Voters are prevented from viewing or interacting with administrative UI panels via `RoleRoute` components.<br>3. **Token Claim Verification**: JWT subject and role claims are cryptographically verified against the database on each request. |

---

## Conclusion
By embedding security controls into the application layer, the network transport layer, the database schema, and database engine triggers, SecureVote achieves defense-in-depth across the entire semester project lifecycle.
